# 实验协议与结果解释

本项目研究图像感知如何转化成可靠的空间抓取位置。最终方法使用 RGB 图像的模型预测及模拟深度传感器，不使用真实类别、真实位置或仿真掩码纠正预测。训练标签、最终评分与显式标记的 oracle 诊断可以使用真值。碰撞几何、物体标识和固定约束夹取属于仿真执行后端，不能据此宣称真实夹爪抓取或未知环境操作。

## 冻结场景和实验条件

1. 先保存完整 `SceneSpec` 场景清单，包括对象、位置、角度、颜色、相机、种子与测试条件。清单文件带 SHA-256 校验，加载时检查内容是否被修改。
2. 所有比较方法在相同场景集合、相同动作预算和相同控制后端上运行。检测框和掩码消融应使用同一个分割模型及同一个权重；版本比较则统一数据、分辨率与训练预算，并保留实际超参数。
3. 标准场景在比较前按统一的稳定性、间距等规则生成。拥挤、遮挡、颜色和光照变化作为单独压力条件。保留原始失败场景，不能按照某种方法是否成功事后删掉测试场景。
4. 先做理想感知诊断：真实目标位姿输入下仍失败时，优先排查控制或路径。oracle 仅是该控制器下的参考上界，失败不构成物理绝对不可达的证明。
5. 图像按独立场景划分训练、验证、测试集。阈值和模型用验证集选择；测试集在冻结方案后评价。来自同一场景的近似视图不得跨集合。
6. 保存数据版本、模型路径与 SHA-256、代码提交、环境、运行参数和场景清单指纹。每个实验使用一个 `run_id` 和独立输出目录。

## 指标定义

| 字段 | 定义与限制 |
|---|---|
| 完整任务成功率 | 完整正确放置所有目标的轮次 / 全部计划中的非空轮次。跳过轮次不算成功，并另报实际评价覆盖率，不能通过跳过难场景提高分数。空场景另列。 |
| 每物体正确放置率 | 正确类别物体放入对应区域的数量 / 场景目标总数。对同一物体重试不会增加物体数。 |
| 至少一次正确放置轮次 | 一轮至少正确放置一个目标；不等同于完整成功或单次夹取成功率。 |
| 抓取尝试与提起 | 尝试数来自实际执行记录；提起按物体去重。提起但未放好、错分拣单独报告。 |
| 错分拣 | 已放置但预测类别或目的区域不正确。评分使用真实类别，执行不能先用真实类别过滤错误预测。 |
| 拒绝事件 | 按阶段和原因记录候选拒绝，可重复涉及同一物体。不能当作唯一目标数、检测准确率或召回率。 |
| 时间 | 逐轮 `initialization_s` 测的是控制器设置（controller setup），不是模型冷启动；另外记录累计感知、定位、动作与轮次 `total_s`，单位秒。模型冷加载和预热另存于 `metadata.models`。缺测是 `null`，不填零。 |

任务耗时包含提前失败的轮次。应同时报告成功率和终止原因，不能将失败更早导致的短耗时解释成更高分拣效率。模型冷启动 `model_load_s` 与一次预热 `warmup_s` 在任务开始前测量，位于 `metadata.models`；共用 checkpoint 的方法共用这些测量，不能把它们相加成多次加载。`initialization_s` 保留字段名以兼容已有记录，其范围仅为逐轮控制器设置。模型加载、预热及场景构建不属于分拣 `total_s`；RGB-D 采集在 `total_s` 内，但不计入 `perception_s`。后者只统计实际调用预测器的累计时间，多次观测的总和不是单张延迟。oracle 不调用预测器，感知/定位缺测应保持 `null`。设置和未细分的开销可能使各阶段之和小于 `total_s`。

单独 `predict` 的 `metadata.json` 保存相同的模型来源和冷加载/预热信息，并另报该预测流程的推理、定位和总时间；预测总时间包含场景构建与图片输出，不与分拣任务的 `total_s` 混比。默认 `evaluate` 仅运行 oracle 与 HSV 后端参考，不能据此宣称验证了学习方法；深度学习对比必须显式指定 `yolo_box yolo_mask` 和训练过的本地权重。

原始 `RunResult` 包含每个物体的各次尝试和最终结果。汇总以该物体最新评分状态计算放置数，保存所有尝试用于失败分析。`completed` 字样与实际正确放置数量不一致时直接报错，不生成误导汇总。

## 输出文件与保护

- `results.jsonl` 是带 `run_id` 的逐轮源记录，内含每次执行结果和阶段拒绝事件。
- `trial_results.csv` 是可用 Excel 查看的一轮一行表，包含准确计数与原始详细字段的 JSON。
- `summary.json` 记录每个方法的完整成功、每物体放置、错分、提起、失败分布和已测时间样本数。
- `metadata.json` 记录实验参数与源结果 SHA-256；源记录修改后加载会报错。
- 记录到源 JSONL 而尚未写完元数据的输出包视为不完整，不可当作正式结果加载。
- 默认拒绝覆盖已有结果，不会自动把新旧实验拼在一起。需要重复实验时使用新目录和新 `run_id`。明确覆盖仅重写这个输出包中的已知文件。
- 配对比较要求每个方法场景集合相同，并拒绝重复的 `(method, scene_id)`。不完整的运行可以作为诊断保存，但须显式关闭配对检查；正式比较仍应使用完整配对数据。

## 原项目复现记录

已有5轮随机场景中，OpenCV、YOLO与Hybrid的完整任务成功均为0/5；每种方法各有1/5轮至少正确放置过一个圆柱。每种方法3轮最终为 `no_valid_targets`，2轮为 `MotionError:joint_limits`。这些是原始基线诊断，不能预填为新方案的结果。

固定演示中，YOLO一次仅放好了盒子，Hybrid一次完成三类。这只说明该固定场景存在完整成功示例；一次演示不等于100%成功率。13张、29实例的高检测指标属于当时的小规模验证集，也不等于任务成功率。

改进后的结果必须实际运行并保留原始记录。若分割质量提高但任务仍失败，也应报告这一结果并定位控制瓶颈。当前固定约束夹取不模拟真实手指接触、摩擦或力闭合；结论限定于该仿真搬运任务。
